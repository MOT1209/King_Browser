KING BROWSER — MULTI-REPOSITORY ENGINEERING MASTER PROMPT

AI Browser Platform, Multi-Repository Research, OpenCode Integration & Secure Agent Control

Project Name: King Browser
Project Type: Open-source desktop browser and AI browser automation platform
Primary Goal: Build a unified, secure, visible desktop browser that combines the strongest reusable ideas and components from three existing open-source projects, with OpenCode integration and precise human control over agent execution.

Repositories to investigate:

1. BrowserOS: https://github.com/browseros-ai/BrowserOS
2. AgenticBrowser: https://github.com/tushar-alt/AgenticBrowser

2. PROJECT VISION

Build King Browser as a dedicated desktop browser designed for users who want an AI coding agent, especially OpenCode, to interact with the web while the user remains in control.

King Browser should combine:

- A real, visible browser.
- Persistent and isolated browser profiles.
- AI-assisted navigation and page interaction.
- OpenCode integration through a verified interface.
- A browser automation toolset.
- Step-by-step execution.
- Phase-by-phase execution.
- Controlled automatic execution.
- Pause, resume, approval, rejection, and emergency stop.
- Activity logs and transparent execution status.
- Security controls and privacy-conscious local storage.
- A professional desktop interface with Arabic and English support.

The application must be a real working product, not a mockup or a collection of disconnected UI components.

The user should be able to see what the agent is doing, understand what it intends to do next, and stop it before an unwanted action occurs whenever the architecture permits.

7.2 Isolated profiles and persistent sessions

- Create and select dedicated browser profiles.
- Keep profile storage separate from the user's normal browser profile.
- Persist cookies and browser storage locally when supported by the selected runtime.
- Restore profiles after application restarts.
- Provide profile clearing and deletion.
- Explain where profile data is stored.
- Handle corrupted or unavailable profile data safely.
- Prevent accidental profile cross-contamination.

The user must enter passwords directly into the visible website.

Never request website passwords through agent prompts, terminal commands, or logs. Never export cookies, session tokens, authorization headers, or passwords to OpenCode.

Do not automatically import existing personal browser credentials. If a profile migration feature is ever added, it must be explicit, transparent, and separately reviewed for security and licensing implications.

Do not bypass CAPTCHA, multi-factor authentication, anti-bot controls, or website access restrictions.

10. EXECUTION CONTROL PANEL

Build a functional control panel containing these controls.

Full Control / Auto-run

Allow permitted actions to run automatically under the selected policy.

Sensitive actions must still require explicit approval.

Next Step

Execute exactly one validated browser action, then pause.

A browser action must have a defined boundary. Internal retries, polling, and recovery must not secretly execute additional user-visible actions.

If an operation cannot be interrupted immediately, report its state honestly.

Next Phase

Execute one explicitly defined phase and pause at its boundary.

Every phase must define:

- Objective.
- Preconditions.
- Permitted actions.
- Maximum action count.
- Completion conditions.
- Failure conditions.
- Required approval points.

Pause

Stop scheduling new actions and reach a safe pause boundary.

Resume

Continue from the saved execution state under the selected mode.

STOP NOW

Provide a prominent, keyboard-accessible emergency stop.

The execution controller must:

- Reject new commands immediately.
- Cancel queued actions.
- Abort in-flight operations when supported.
- Prevent further actions until an explicit resume or new run is authorized.
- Record the stop reason and actual final state.
- Prevent delayed commands from continuing after the stop.
- Report honestly when a running operation cannot be interrupted instantly.

Approve / Reject

Display the pending action, destination domain, and a clear explanation of the intended result.

Approval must be limited to that specific action and must expire if the underlying action changes.

Rejecting an action must prevent its execution.

Emergency Close

Allow the user to close the automation session safely without falsely claiming that every underlying process has terminated if it has not.

11. AUTHORITATIVE EXECUTION ENGINE

Implement a single authoritative state machine.

Suggested states:

- "idle"
- "running"
- "paused"
- "awaiting_approval"
- "stopping"
- "stopped"
- "error"

Requirements:

- No duplicate action execution.
- No uncontrolled parallel actions.
- No race conditions between pause, resume, approval, and stop.
- No hidden background execution after stop.
- Bounded action queues.
- Explicit operation timeouts.
- Safe cancellation and recovery behavior.
- Backend enforcement of execution state.
- Persisted run history where appropriate.
- Clear distinction between requested, running, completed, failed, and cancelled actions.

Do not rely on disabling UI buttons as the only security boundary.

The execution engine must reject invalid state transitions and unauthorized commands even if the UI is bypassed.
